# business_plan.md (финальная версия 2)

## Идея / проблема
Телеграм-бот уже работает (aiogram 3) и реагирует на `start`, `store`, `support`.
Цель — личный хаб: на `/start` появляется дашборд с функциями, новые модули
добавляются легко, без переписывания ядра.

## Целевая аудитория
- Сейчас: владелец бота (один пользователь).
- Потом: возможно другие. Данные с самого начала изолируются по `telegram_user_id`.

## Функции (v1)
1. **Календарь.**
   - **Чтение:** опубликованный iCloud-календарь (ссылка `webcal://` / `https://….ics`),
     read-only фид без авторизации. Бот скачивает `.ics`, парсит события, ставит напоминания.
   - **Запись (через подтверждение):** бот НЕ пишет в календарь напрямую. Он генерирует
     событие как `.ics`-файл / ссылку и присылает юзеру; юзер тапает, открывается его
     календарь с готовым событием и **сам подтверждает** добавление. Авторизация не нужна.
2. **«Шкаф памяти».**
   - Создание / выбор полок (shelves).
   - Заметки внутри полок (создать / посмотреть / редактировать / удалить).
3. **Напоминания (пуш = сообщение от бота).**
   - Юзер задаёт время и интервалы сам.
   - У каждого напоминания **свой редактируемый текст сообщения** (можно изменить после создания).
   - В заданное время бот присылает именно этот текст.

## Идентификация и безопасность
- `telegram_user_id` — опознаёт юзера внутри бота, фильтрует данные.
- Календарь — только публичный ICS-URL для чтения; для записи секретов нет (подтверждает юзер).
- Рекомендация: публиковать **отдельный календарь «Bot»**, а не основной.
- URL-подписка считается полуприватной (по ссылке видно события) → в логи не выводится.
- Единственный настоящий секрет проекта — `BOT_TOKEN` (в `.env`, не в коде/логах).

## Технологии (с учётом хостинга Render free)
- **python-telegram-bot 22.3** (Python, async) + **FastAPI** webhook — так бот реально
  написан и год в проде (НЕ aiogram, как ошибочно стояло в ранней версии плана).
  Сервер спит, входящий апдейт его будит, постоянные деплои не нужны. Переиспользуем как есть.
- **БД (внешняя):** локальные файлы Render free стираются и при засыпании, поэтому хранилище
  держим вне инстанса.
  - **Решено: Neon** (бесплатный Postgres, не истекает) через `DATABASE_URL`, SQLAlchemy async
    — в текущем боте хранилища нет, заводим с нуля.
    НЕ локальный SQLite и НЕ встроенный Render-Postgres (истекает за 30 дней). Альтернатива — Supabase.
- **Напоминания (только таймер):** webhook будит сервер на апдейтах юзера, но напоминание должно
  сработать в заданное время и без активности. Поэтому лёгкий внешний пинг (cron-job.org /
  GitHub Actions) на эндпоинт `/tick` раз в N минут → бот проверяет «созревшие» напоминания в БД
  и шлёт их. Точность = интервал пинга. Для «Шкафа» это не нужно.
- **Календарь:** `httpx` (скачивание фида) + `icalendar` (парсинг при чтении и сборка `.ics` при записи).
- **Диалоги (FSM):** состояния пошаговых диалогов в БД (не в памяти — иначе теряются при
  засыпании). В python-telegram-bot — через persistence/собственное хранение шага в БД.

## Архитектура (расширяемость)
Модульная: ядро (дашборд, реестр модулей, БД) + папки `features/*`.
Каждый модуль регистрирует свою кнопку и свои ptb-handlers через реестр.
**Новый модуль = новая папка + одна строка в реестре**, ядро не трогаем.
Текущая плоская структура (`handlers/`, `DataBase/`) постепенно переезжает в эту схему.

```
bot/
  bot_start.py       # сборка ApplicationBuilder + FastAPI webhook, регистрация handlers (уже есть)
  config.py          # env: BOT_TOKEN, DATABASE_URL, WEBHOOK_URL
  core/
    dashboard.py     # /start -> строит инлайн-меню из реестра модулей
    registry.py      # список модулей (кнопка + регистрация handlers)
  db/ models.py      # User, Shelf, Note, Reminder, CalendarFeed (SQLAlchemy async, Neon)
  features/
    shelves/         # полки + заметки
    reminders/       # свои напоминания (свой текст) + эндпоинт /tick (внешний cron)
    calendar/        # подписка по URL (чтение) + генерация .ics (запись через подтверждение)
```

## Грубые шаги
1. БД-схема + авто-регистрация юзера по `tg_id` на `/start`.
2. Скелет дашборда (инлайн-меню + роутинг callback + реестр модулей).
3. Модуль «Шкаф» (полки + заметки).
4. Модуль напоминаний (своё время/интервалы + редактируемый текст; проверка через /tick + внешний cron).
5. Модуль «Календарь» (чтение по URL -> напоминания; генерация .ics для добавления событий).
6. Тесты + обновление `changelog.md` / `improvements.md` на каждом шаге.

## Критерии успеха
- `/start` открывает дашборд; виден только свой контент.
- Полки и заметки создаются / читаются / редактируются / удаляются.
- Напоминание срабатывает вовремя, текст можно отредактировать, переживает рестарт.
- URL-подписка читается, события подтягиваются, по ним приходят напоминания.
- Бот генерирует `.ics`, юзер открывает и подтверждает добавление в свой календарь.
- Новый модуль добавляется без изменений в ядре.

## Открытые вопросы / риски
- Публичный URL = любой со ссылкой видит события -> отдельный календарь «Bot».
- У Apple опубликованный календарь обновляется с задержкой (кэш) -> синк раз в N минут.
- Подобрать интервал поллинга и обработку ошибок скачивания ICS.
- Связь шкаф<->напоминания (превращать заметку в напоминание): решено ОТЛОЖИТЬ на позже.
- Холодный старт free-инстанса ~30–60 сек при пробуждении (для напоминаний приемлемо).
- Напоминания требуют внешнего пинга на /tick по расписанию (webhook сам по таймеру не будит).
